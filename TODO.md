# TODO

- Full-text session search. The sidebar search matches only a session's name, directory and first user message, and only the first 256 KB of that message, which the gateway caps so a huge one cannot push the session index over its memory bound. Pi's `/resume` picker matches all message text, with fuzzy tokens, `"phrases"` and `re:` patterns. Matching it means indexing message text in the gateway, which costs memory.
- Palette commands that Pi runs through the composer: clone, compact, export, reload, and Pi's skills, prompt templates and extension commands. Running them today means submitting the composer, which would take a draft and its attachments with it. They need a way to run that leaves the composer alone.
- More palette commands: show only a project or tag, show or hide Pi CLI sessions, delete session, notifications, gateway update.
- A way into the palette without a keyboard, and an entry in the desktop app's menu.
- Faster first start. The gateway's first start, and any start after the saved session cache's version changes, still parses every session file one at a time: 28 s for 1.7 GB of sessions. Parsing them in parallel took 6.8 s with 4 workers and 4.0 s with 8 in a rough test, for about twice the memory (175 MB to 350 MB).
- Count HTTP errors from event polls as lost connection. "Connection lost. Retrying…" appears after two `/events` requests in a row fail outright. An error response, such as a proxy's 502 while the gateway is down, is retried silently, so behind a proxy a gateway that goes down mid-run shows no warning until the page is refocused.
- Red takeover errors. A failed takeover prints its error inside the session sync banner in muted grey instead of red, because `.session-sync-banner span` outranks `.session-sync-error`.
- Personal skills per user in multi-user mode. All users share the gateway's skills. Passing a user's own skills to Pi with `--skill` is not enough: a shared skill with the same name wins over one passed that way, and subagents do not seem to inherit the flag (not verified).
- A single GitHub row in the Environment dialog that fills in the variables from a token, or imports the `gh` login from the desktop app's computer. Today the user fills in the block by hand, with the name and email twice. Filling in the name and email means asking GitHub's API who the token belongs to, and importing a login needs the desktop app, because a browser cannot read it.
- Apply changed environment variables to a new session that has no message yet. It keeps the values it started with, because it exists only inside its Pi process: a restart would have to carry over the model, thinking level and name chosen before the first message.
- Live events after Pi restarts for changed environment variables. Event numbers start again with each Pi process. A second tab or device that first polls after the new process has emitted as many events as the old one had skips that many events of the new turn in its live view, until the session reloads. Continuing the numbers across the restart means renumbering inside the RPC client, because queue updates and live snapshots carry the same numbers.
- Entries over 64 MB. The gateway skips such an entry when it indexes a session, so the history before it drops out of view, and when Pi CLI appends one, reconciling the append fails and the session asks to be taken over. Handling them means reading the entry's id and parent with the streaming scanner, keeping a stub for it in the index and showing a placeholder where it would render. The largest entry in real sessions so far is 7.8 MB.
- Keep a code block's Copy button off its code on touch screens. There the button is always shown, and it covers the end of a long line.
- Live output for `!` and `!!` commands. Pi CLI shows a command's output as it arrives, and Pi streams it over RPC as `bash_execution_update` events, but Gripi drops them and shows the output once the command ends. The running card itself only appears with the next event poll, a second or two after sending. Streaming it means keeping the output so far for a reload or another tab mid-run, and bounding how much of a very large output is kept.
- Wipe in the first line of thinking. Live thinking shows "Thinking…" until its first paragraph is finished, and that paragraph's first line then replaces the placeholder at once, because the wipe only reveals what lies below the body's previous height.
- Keep Markdown images from popping in after a wipe. An image in a streamed reply loads after its block has wiped in, so it appears at once, pushes the text below it down, and a following view does not scroll to it. This is not new with paragraph streaming.
- Show the finished lines of a long code block while it streams. Replies and thinking show only finished blocks, so a long code block appears only once its closing fence arrives, which can take tens of seconds. Inside an open fence, the finished lines could be shown without anything reflowing, because Markdown renders an unclosed fence as code to the end.
