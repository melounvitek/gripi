# TODO

- Full-text session search. The sidebar search matches only a session's name, directory and first user message, and of a first message whose entry is over 256 KB only the first 8 KB, which the gateway keeps so a huge one cannot push the session index over its memory bound. Pi's `/resume` picker also matches the session id and the text of every user and assistant message, with fuzzy tokens, `"phrases"` and `re:` patterns. Matching it means indexing message text in the gateway, which costs memory.
- Palette commands that Pi runs through the composer: clone, compact, export, reload, and Pi's skills, prompt templates and extension commands. The browser runs them by submitting the composer, which would take a draft and its attachments with it. The gateway already has routes for compact, clone and export, and the rest can go to `/prompt` without the composer's draft, so what is missing is the browser side.
- More palette commands: show only a project or tag, show or hide Pi CLI sessions, delete session, notifications, gateway update.
- A way into the palette without a keyboard, and an entry in the desktop app's menu.
- Faster first start. The gateway's first start, and any start after the saved session cache's version changes, still parses every session file one at a time, behind one lock (`buildMu`): 28 s for 1.7 GB of sessions. Parsing them in parallel took 6.8 s with 4 workers and 4.0 s with 8 in a rough test, for about twice the memory (175 MB to 350 MB).
- Count HTTP errors from event polls as lost connection. "Connection lost. Retrying…" appears after two `/events` requests in a row fail outright. An error response, such as a proxy's 502 while the gateway is down, is retried silently, so behind a proxy a gateway that goes down mid-run shows no warning until the page is refocused.
- Personal skills per user in multi-user mode. All users share the gateway's skills. Passing a user's own skills to Pi with `--skill` is not enough: a shared skill with the same name wins over one passed that way, and the subagent extension starts subagents without the flag.
- Fill in the Environment dialog's GitHub variables from a token, or import the `gh` login from the desktop app's computer. The dialog's GitHub row only adds a block of empty variables, which the user fills in by hand, with the name and email twice. Filling in the name and email means asking GitHub's API who the token belongs to, and importing a login needs the desktop app, because a browser cannot read it.
- Apply changed environment variables to a new session that has no message yet. It keeps the values it started with, because it exists only inside its Pi process: a restart would have to carry over the model, thinking level and name chosen before the first message. Until then, the dialog's "Changes apply from your next message in each session" is wrong for such a session.
- Entries over 64 MB. The gateway skips such an entry when it indexes a session, so the history before it drops out of view. When one is appended while the gateway's Pi runs the session, reconciling the append fails and the session shows a conflict, and while one is the session file's last line, the session cannot be read or taken over at all. Handling them means reading the entry's id and parent with the streaming scanner in the index, the file snapshot and the append check, keeping a stub for it in the index and showing a placeholder where it would render. The largest entry in real sessions so far is 7.8 MB.
- Keep a code block's Copy button off its code. The button is always shown, and it covers the end of a long line, more so on narrow screens, where it is taller.
- Live output for `!` and `!!` commands. Pi CLI shows a command's output as it arrives, and Pi streams it over RPC as `bash_execution_update` events, but Gripi drops them and shows the output once the command ends. The running card itself only appears with the next event poll, a second or two after sending. Streaming it means keeping the output so far for a reload or another tab mid-run, and bounding how much of a very large output is kept.
- Wipe in the first line of thinking. Live thinking shows "Thinking…" until its first paragraph is finished, and that paragraph's first line then replaces the placeholder at once, because the wipe only reveals what lies below the body's previous height.
- Keep Markdown images from popping in after a wipe. An image in a streamed reply loads after its block has wiped in, so it appears at once, pushes the text below it down, and a following view does not scroll to it. Only same-origin images load at all: the content security policy blocks others and the sanitizer drops `data:` images. This is not new with paragraph streaming.
- Show the finished lines of a long code block while it streams. Replies and thinking show only finished blocks, so a long code block appears only once its closing fence arrives, which can take tens of seconds. Inside an open fence, the finished lines could be shown without anything reflowing, because Markdown renders an unclosed fence as code to the end.
- Show live tool results once. A read, edit or write error, and a write success, appears twice on its tool card while it runs, because Pi sends the tool result in both `message_start` and `message_end` and the live renderer appends it each time. A reload shows it once.
- Keep a widget's placement across a reload. The live snapshot drops `widgetPlacement`, so a widget an extension put below the editor comes back above it. An E2E test in `live_extension_ui.spec.js` expects this.
- A Gripi-owned live event model. The browser still parses Pi's events, live snapshots, model settings, fork messages and trees, which the server passes through as opaque JSON (`docs/architecture.md`), and it repeats in JavaScript the projection Go already does for history. Translating Pi's events in the adapter into a few typed events built by the same Go projection would remove the duplicate, which has drifted in edge cases such as tool-argument JSON and timestamps.
