# Backend architecture

The gateway runs coding agents through a small contract in `internal/agent`, and Pi is one adapter behind it. Hermes Agent is a second, experimental one, which only `GRIPI_HERMES` turns on. Parts of the contract still follow Pi (see [Pi-shaped parts](#pi-shaped-parts)).

## Layers

- `cmd/gripi` builds the Pi adapter from the configuration and passes it to the server. With `GRIPI_HERMES`, it passes a `Router` instead, which serves Pi and Hermes as one adapter.
- `internal/server` serves the browser, the local API and the `gripi` commands. It reaches the agent only through `internal/agent`.
- `internal/agent` is the core: neutral types, the contract, and the machinery that runs session clients (the client registry, pending sessions, maintenance, diagnostics, starting and branching sessions). It imports no adapter and no gateway package.
- `internal/agent/hermes` is the Hermes adapter. It runs every Hermes session in one `hermes acp` process and speaks ACP, the Agent Client Protocol, to it.
- `internal/agent/pi` is the Pi adapter. Its subpackages are `rpc` (Pi's RPC client and process), `settings` (Pi's settings files) and `sessionfile` (the reader of Pi's JSONL session files, and the synchronizer that guards them against Pi CLI).
- `internal/sessions` keeps what the gateway owns about sessions: read state, pins, tags, completions, projects, attachments and path suggestions.
- `internal/worker` runs the sessions placed on [workers](configuration.md#workers): it connects to them with the system `ssh`, copies Pi there, records which session is on which worker, moves sessions there and back, keeps the workers' logins current and forwards ports. Its subpackages are `helper` (the worker's side, `gripi worker serve`, which runs each session's Pi in a cgroup of its own under a lease), `mirror` (the engine that keeps main's copy of a moved session's selected folders or of its file equal to the worker's at each barrier, and makes one-off copies in either direction), `reconcile` (main's side of a session's move: the base that the move's copy starts from, and the return, which brings the worker's changes to main's folders and keeps aside the worker's version of what main changed too, what the session made outside its worktrees, and, once it fails, what it hasn't brought yet), `auth` (the worker's `auth.json`, without refresh tokens), `view` (the private view in which processes on a worker see the worker user's home folder at main's home folder, and a moved session's view of its copy) and `dockerproxy` (the Docker socket of a moved session, which moves host paths to its copy and the worker user's home folder).

Only `cmd/gripi` and an adapter itself import that adapter's package. The worker packages belong to the gateway, so like the server they reach agents only through the core. `internal/architecture_test.go` checks these rules for production code; tests may still build real Pi clients.

## Adapters

An adapter implements `agent.Adapter`, which starts a `Client` for each session and returns the adapter's `Store`, `Guard` and `Composer`:

- A `Client` serves one session, which need not be one process.
- The `Store` lists and reads saved sessions. Its keys are opaque to the gateway; Pi's are the absolute paths of its session files.
- The `Guard` keeps the gateway from writing a session that someone else writes, such as Pi CLI. An agent whose sessions nobody else writes can pass every call through.
- The `Composer` says how the agent reads what the user types, such as Pi's `!` and `/` commands.

A `Router` sends each session to the agent whose store accepts its key: Pi's keys are paths, Hermes's `hermes:<session ID>`. It names each session's agent in `Session.Agent`, which keeps Hermes's sessions out of the session list, and starts a new session with the agent that `StartOptions.Agent` names. The server keeps one current Hermes conversation, which the Hermes panel shows. Without Hermes, the gateway gets the Pi adapter itself, and so works as it did before.

Features that only some agents have, such as the prompt queue, shell commands, tree navigation, model selection and extension dialogs, are optional interfaces in `internal/agent/capabilities.go`. The server checks for them with type assertions, and the Pi adapter asserts at compile time that its client implements them.

## Workers

The Pi adapter doesn't know about workers. `cmd/gripi` passes it an `agent.Launcher` (`internal/agent/launcher.go`), which the worker manager implements. For a session on a worker, the launcher has the worker's helper start Pi there, and returns an `ssh` command that carries Pi's RPC, which the adapter's RPC client runs in Pi's place; for any other session it returns no command, and Pi starts on main. When the launcher loses the process, such as with the connection, `Process.Lost` ends the running step with an unknown outcome. The server reaches the manager only through its own `Workers` and `WorkerPlacement` interfaces, which `cmd/gripi` fills.

The helper is the gateway's own executable, so builds are static (`CGO_ENABLED=0`). The `gripi worker` commands live in `cmd/gripi`, including the internal ones that main runs on a worker over `ssh`: `serve`, `attach`, `receive`, `mirror`, `enter` and `sudo`, and `move-host`, which the helper runs. When the worker user's home folder differs from main's, `serve` runs the whole helper in the private view, so Pi and the mirrors see main's paths. Like `attach` and `mirror`, `receive` only connects main's channel to the helper, which makes main's copies itself, so that they see the files as its mirrors do: each view shows what was next to main's home folder when it started. Main runs its checks there through `enter`, which makes a view also when the worker user's home folder is main's, because each moved session needs one. The view's namespaces belong to new processes, because Go's runtime has threads, which `unshare(2)` refuses: `view.Init`, first in `main`, lets gripi start itself again to enter it.

A session that moves alone runs on a private copy of its repository, in the helper's `copies/` folder, which main fills from its shadow of the session's folders. Each process of the move starts in a view of its own, nested in the helper's (`view.Move`), where the private roots, the folders directly in main's home folder that hold the repository, show the copy: the session's Pi, in the session's cgroup, and the move's host, `move-host`, in a cgroup of the move, which runs the mirrors of the copy and of the session's file and the session's Docker socket. The helper asks the host over a socket for what needs the move's view, such as barriers or the folders that Git ignores, which a new copy takes from earlier ones. The Pi adapter's store reads which paths a session's tool calls named (`agent.ToolPathsReader`), from which the manager picks the worktrees that the copy gets.

`gripi sudo` in a session on a worker runs sudo where setuid works, outside every view: main runs `gripi worker sudo` under the worker user's systemd, from where it may start sudo in the session's cgroup. sudo runs `nsenter`, which enters the mount namespace of the session's Pi. Each time that sudo asks for the password, its askpass program, gripi, asks the helper, which asks main over the control channel, so that main can ask the user again after sudo rejected a password, as it does for sudo on main.

## Scratch sessions

A scratch session starts with `StartOptions.Scratch`, for which the Pi adapter starts Pi with `--no-session`. Pi then names no session file, so the session keeps the pending key that `agent.StartNewSession` gives it, and the server's `scratchSessions` (`internal/server/scratch_routes.go`) keep it out of every list and refuse the routes that need a saved session. Its key stays a scratch key after it ends, so that a request already under way can't start a saved session under it, and the registry's factory refuses scratch keys, as Pi would save a session that it started again. Pages read its history through the optional `agent.MemoryHistory`, which the Pi client implements with two commands of Gripi's extension, `gripi_history` and `gripi_history_image`, and the session file renderer over the entries in memory (`Store.WindowFromEntries`). Prompt bodies and forms stay in memory, so a scratch prompt's images never reach a file. The model and thinking level chosen in a scratch session, through `/sessions/model_settings` or `/sessions/cycle_thinking`, go to `scratchModels`, a state file by user, and `agent.ChooseForNewSession` gives them to the user's next one. `/scratch/continue` has a third command of the extension, `gripi_save_session`, write the session to a file in its folder, from which the new session starts as Pi's fork in the chosen folder, as **Move to another folder** does, and then ends the scratch session. The fork's header names that file as its parent, which is gone by then.

## Asking Pi to find sessions

`POST /sessions/find_with_pi` (`internal/server/pi_search_routes.go`) starts Pi for one request in a scratch session folder, with `StartOptions.Scratch` and `StartOptions.FindSessions`, but registers no client, so nothing lists or reaches it. For `FindSessions`, the Pi adapter allows only the `search_sessions` and `show_session` tools and passes no skill, and sets `GRIPI_FIND_SESSIONS` to the gateway's executable, which turns those tools on in Gripi's extension. They run that executable's `gripi search` and `gripi show` with the user's `GRIPI_USER_TOKEN`. The route reads the run's last reply from `RunEnded` once `RunSettled` reports it, and keeps the words of it that are the IDs of sessions in the user's sidebar listing. The request's end, a newer search of the same user, the gateway stopping or the timeout close Pi and remove its folder. The sidebar lists the sessions in `session_found` with those that match `session_search`.

## Pi-shaped parts

- The browser still reads Pi's formats: live events and snapshots, model settings, fork messages and session trees. The adapter returns them as opaque JSON that the core and server pass through without reading; only what the server itself reads is typed. Server-rendered history uses the core's `Message`, whose vocabulary is still Pi's. The Hermes adapter therefore turns ACP's updates into Pi's live events, and projects the same updates onto `Message`s for the history.
- Some core error texts and the diagnostics component still name Pi, because users and logs see them.
- Every `Client` must switch its session in place for a new session (`NewSession`), and a branch whose client keeps serving the old session fails on purpose. `Cancel` doesn't report the prompts it dropped.
