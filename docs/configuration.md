# Configuration

Gripi reads settings from `~/.config/gripi/env`, one `NAME=value` per line; set each variable only once. Variables set in the process environment override the file. Restart the gateway after changing a setting. Restarting stops any running Pi work.

Boolean settings accept `1`, `true`, `yes`, or `on` for true and `0`, `false`, `no`, `off`, or an empty value for false, in any letter case. Any other value stops the gateway at startup, so a typo cannot silently change its behavior.

## Settings

| Setting | Default | Section |

## Server address

The gateway listens on `127.0.0.1:4567`, so only the same machine can reach it. To change this, set `GRIPI_HOST` and `GRIPI_PORT` in the command or the [systemd unit](examples.md#keep-the-gateway-running-with-systemd). Gripi does not read them from `~/.config/gripi/env`:

```sh
GRIPI_HOST=100.x.y.z GRIPI_PORT=4568 ~/.local/share/gripi/bin/start
```

Gripi rejects plain HTTP from other machines. For remote access, prefer HTTPS through [Tailscale Serve](examples.md#https-through-tailscale-serve) or another trusted private reverse proxy.

To allow a [direct VPN connection](examples.md#direct-vpn-connection) over plain HTTP, set:

```sh
GRIPI_ALLOW_INSECURE_REMOTE_HTTP=1
```

Do not use this setting for ordinary LAN or Wi-Fi access. Avoid binding to `0.0.0.0` or `::` unless network access to the machine is already restricted. If you do, list every hostname or IP address that clients use in `GRIPI_PERMITTED_HOSTS`.

## Reverse proxy

Gripi accepts requests only for the hostname or IP address it listens on. When a reverse proxy, such as Tailscale Serve, uses another name, list that name and let Gripi trust the proxy’s headers:

```sh
GRIPI_PERMITTED_HOSTS=gateway.example.ts.net,gripi.example.net
GRIPI_TRUST_PROXY_HEADERS=1
```

`GRIPI_PERMITTED_HOSTS` is a comma-separated list of hostnames, IPv4 addresses, or bracketed IPv6 addresses. Ports are allowed but ignored when matching.

Only enable `GRIPI_TRUST_PROXY_HEADERS` when all traffic goes through a trusted private proxy that overwrites the `X-Forwarded-Proto`, `X-Forwarded-Host`, and `X-Forwarded-Port` headers. If clients can reach the gateway without the proxy, they can fake these headers. Leave it off for direct localhost, LAN, and VPN connections.

If a request uses a hostname that is not configured, Gripi blocks it and shows the setting to add. Follow that advice only if you recognize the hostname as your Gripi address.

The gateway accepts request bodies up to 64 MiB; this limit is fixed. Set the same or a lower limit in your proxy, and do not let the proxy buffer request bodies without a limit.

## Access approval

In single-user mode, every new browser must be approved once. The access page offers two options:

- Enter the admin password.
- Select **Ask access**. The page shows a code, and browsers that are already approved show a prompt with **Allow** and **Deny**. Allow only if the code matches the one on the new device.

Approval is saved per browser and address, so the desktop app and each URL, such as `localhost` and a `ts.net` name, are approved separately.

The admin password is `GRIPI_ADMIN_PASSWORD` in `~/.config/gripi/env`. The gateway does not start without it unless approval is disabled. The installer generates it, and `~/.local/share/gripi/bin/gripi-password` adds one if it is missing. To change it, edit the file and restart the gateway. Browsers that are already approved stay approved, so if the password leaks, also remove browsers you do not recognize.

Approved browsers are listed under `approved_browsers` in `~/.pi/gripi/browser-access.json`, with their approval time and user agent. To remove a browser, delete its entry. The change applies to the browser’s next request.

### Disabling approval

```sh
GRIPI_BROWSER_AUTH_DISABLED=1
```

This lets anyone who can reach the port use Pi on the gateway machine. Only use it when localhost, a VPN, firewall rules, or another private network boundary already limits access to trusted devices and users.

## Multi-user mode

By default, Gripi shows all Pi sessions to a single trusted user. To give each user a private session list, enable multi-user mode:

```sh
GRIPI_MULTI_USER_MODE=1
```

Each user generates a private user token and sees only their own sessions. The same token shows the same sessions in any browser. Tokens cannot be recovered, so users must store them safely. Sessions created before multi-user mode was enabled, or in Pi CLI, have no owner and are not shown to anyone.

User-token approval replaces browser approval:

- The first user is created with the admin password.
- Later users generate a token and select **Ask for access**. An approved user then approves the request.

Approved users are listed under `approved_workspaces` in `~/.pi/gripi/workspace-access.json`. Entries contain an ID derived from the token, not a name. To find a user’s ID, look up one of their session files in `~/.pi/gripi/session-owners.json`; delete the matching entry to revoke access. The user’s saved [environment variables](#environment-variables) stay in `~/.pi/gripi/environment.json` under the same ID until you delete them there. With `GRIPI_BROWSER_AUTH_DISABLED=1`, every new token is approved automatically and stays approved until it is removed from that file. Only use that combination when every client that can reach the gateway is trusted.

Multi-user mode separates session lists and [environment variables](#environment-variables), not permissions: all users run commands as the same OS user and share settings such as the selected model and thinking level. For the same reason, one user’s variables are not secret from the others.

The [`gripi` command](../README.md#command-line) is unavailable in multi-user mode, because it would show every user’s sessions.

## Environment variables

Gripi can save environment variables for Pi, for example your own [GitHub](#github) token on a shared gateway. Pi and every command it runs get them on top of the gateway’s own environment, and a saved variable replaces a gateway variable of the same name.

Edit them in the Environment dialog, opened with the key icon in the sidebar header or **Environment…** in the Ctrl+K palette. The list shows names only; a value is shown only while its row is open for editing. Pasting several `NAME=value` lines adds them at once, and lines starting with `#` are ignored.

In single-user mode, the variables apply to every Gripi session. In [multi-user mode](#multi-user-mode), each user has their own set, applied only to the sessions that user owns. A session with no owner gets none. Variables saved in one mode are not used or shown in the other, but they stay in the file.

A change applies from the next message or `!` command in each session. If the session’s Pi process is idle and started before the change, Gripi restarts it first, which loses process-only state in the same way as [stopping an idle process](#pi-process-lifetime). A running turn keeps the old values until it ends, and so do messages steered or queued during it.

A new session that has no message yet keeps the values it started with, so its first message still uses them. Pi CLI in a terminal does not get the variables; `gripi send` does, because it goes through the same path as a message from the browser.

Names consist of letters, digits, and `_`, and cannot start with a digit. `HOME`, `GRIPI_*`, and `PI_CODING_AGENT_*` are refused, because they move Gripi’s or Pi’s directories. A value cannot be empty and is at most 16 KiB long. Each user can save at most 100 variables.

The values are stored as plain text in `~/.pi/gripi/environment.json`, which only the gateway’s OS user can read; nothing Pi-owned changes. In multi-user mode, the variables separate identity, not secrets: every user runs commands as that OS user, so one user’s Pi can read the file with another user’s values. For real separation, run one gateway per OS user.

### GitHub

The main use is acting as yourself on GitHub from a shared gateway. `GH_TOKEN` alone only changes `gh`: pull requests, issues, and API calls. Commits and `git push` still use the gateway’s identity unless your name, email, and git configuration are set too.

**+ add GitHub variables** in the dialog opens the whole set, with the first five values empty:

```txt
# gh: pull requests, issues, API
GH_TOKEN=
# your name and email on commits
GIT_AUTHOR_NAME=
GIT_AUTHOR_EMAIL=
GIT_COMMITTER_NAME=
GIT_COMMITTER_EMAIL=
# git push over HTTPS with your token, also for SSH remotes; leave as is
GIT_CONFIG_COUNT=2
GIT_CONFIG_KEY_0=url.https://github.com/.insteadOf
GIT_CONFIG_VALUE_0=git@github.com:
GIT_CONFIG_KEY_1=credential.https://github.com.helper
GIT_CONFIG_VALUE_1=!gh auth git-credential
```

Fill in the empty values and save:

- `GH_TOKEN` is your GitHub token, used by `gh`. Create it at <https://github.com/settings/tokens>. For a classic token, `gh` asks for at least the `repo`, `read:org`, and `gist` scopes.
- The `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables put your name and email on commits.
- The `GIT_CONFIG_*` variables make git reach GitHub over HTTPS and ask `gh` for the token, so pushes to `git@github.com:` remotes use your token too. They need `gh` installed on the gateway machine. Remotes written as `ssh://git@github.com/…` are not covered and would need one more key and value pair.

On the gateway machine, `gh` must be the only credential helper git uses for GitHub. Make it so by running this once as the gateway’s OS user:

```sh
gh auth setup-git --hostname github.com --force
```

If git also uses another helper there, such as the macOS keychain or `store`, a login saved in it is used instead of your token, and a successful push saves the pushing user’s token in it for everyone.

If `GH_TOKEN` is saved without the rest, the dialog warns that commits and `git push` still use the gateway’s identity and offers **+ add the rest for GitHub**.

## Pinned session directories

List frequently used directories in `~/.config/gripi/pinned-dirs` to keep them available in the New Session dialog:

```txt
/home/alice/projects/gripi
/home/alice/projects/another-project
```

Use one directory per line. Blank lines and `#` comments are ignored.

## Session tags

Add tags with the tag icon in the conversation header or **Tags…** in a session’s menu. Select a tag in the sidebar to filter by it; pinned sessions stay visible. Forks and clones keep their tags.

Tags are lowercased, up to 64 characters long, and limited to 32 per session. They are stored in `~/.pi/gripi/session-tags.json`, not in Pi’s session files, and are private to each user in multi-user mode.

## Project resource approval

Gripi starts Pi with `--approve`, so project-local settings, extensions, skills, prompts, themes, system prompts, and packages load without asking. Pi CLI asks before trusting a project. Project extensions and package installation scripts can run any code as the gateway OS user, so only open projects you trust.

To turn automatic approval off:

```sh
GRIPI_AUTO_APPROVE_PROJECTS=0
```

Pi then applies its normal trust rules, including saved trust decisions and the global `defaultProjectTrust` setting. Gripi cannot show Pi’s trust prompt, so with the default `"ask"` setting, project resources stay disabled until you trust the directory in Pi CLI. Gripi never changes Pi’s saved decisions in `~/.pi/agent/trust.json`.

## Custom Pi runtime

By default, Gripi runs `pi` from `PATH`. To use specific executables, set both variables:

```sh
GRIPI_NODE=/path/to/node
GRIPI_PI=/path/to/pi
```

The selected runtime must already work, authenticated and configured, for the gateway’s OS user.

## Session location

Gripi lists sessions from `~/.pi/agent/sessions`. If Pi stores sessions somewhere else, for example because `PI_CODING_AGENT_DIR` is set, point Gripi there:

```sh
GRIPI_SESSIONS_ROOT=/path/to/sessions
```

## Pi process lifetime

Gripi stops a Pi process about five minutes after the last user action. Background polling from open tabs does not count, so a forgotten tab cannot keep Pi running. Running agent turns, compaction, shell commands, and new sessions that Pi has not saved yet are not stopped for being idle.

Using the session again starts a new Pi process. The conversation is kept in Pi’s session file, but the first response takes longer, and process-only state, such as open extension dialogs, is lost.

```sh
GRIPI_RPC_IDLE_TIMEOUT_SECONDS=300
GRIPI_RPC_IDLE_SWEEP_SECONDS=30
```

The timeout is a whole number of seconds; `0` disables it. The sweep interval sets how often Gripi checks for idle processes and can be any positive number of seconds.

## Web Push notifications

Turn notifications on with the bell icon in the sidebar header, which is orange when they are on and crossed out when they are off or blocked. On iPhone and iPad, this requires iOS/iPadOS 16.4 or newer and Gripi added to the Home Screen.

Gripi sends the notification one minute after a reply finishes, unless the session has been read in any of your Gripi clients or is open and focused in one of them. A client that disconnects stops counting as focused after about 30 seconds.

Web Push requires HTTPS, such as [Tailscale Serve](examples.md#https-through-tailscale-serve). The gateway also needs outbound HTTPS access to the browser’s push service. Delivery is best-effort.

Gripi creates its push keys on first use in `~/.pi/gripi/web-push-vapid.json` and stores subscriptions in `~/.pi/gripi/push-subscriptions.json`. Keep the key file: replacing it breaks existing subscriptions, and every device must turn notifications on again. Both files contain secrets, so do not share them.

The `/notification-test` page registers the current browser and sends a test notification.

## Resource monitoring

On Linux with cgroup v2, Gripi can show RAM and CPU usage in the sidebar:

```sh
GRIPI_RESOURCE_MONITORING=1
```

The indicator shows the cgroup total, the gateway’s memory, and the memory and number of Pi processes, including subagents. The parts may not add up to the total because shared memory is counted differently. 100% CPU means one full core. If cgroup data is not available, the indicator stays hidden.

## RPC diagnostics

To investigate a stuck Pi process, log its lifecycle:

```sh
GRIPI_RPC_DIAGNOSTICS=1
```

The log includes request and session paths, RPC command types and IDs, rejections, responses, timeouts, and process shutdowns. Prompts and conversation contents are never logged.

## Self-updates

On Linux and macOS, Gripi checks `origin/master` when the page loads and shows a sidebar control when an update is available. Anyone who can use the gateway can start an update.

The update waits until no Pi session is running. Gripi builds and tests the new version in a separate worktree first, so a failed update leaves the running gateway unchanged. If a later step fails, Gripi restores the previous version. Updating needs network access and Pi CLI on the gateway’s `PATH`, and can take a few minutes.

The checkout must:

- be on `master`
- have no changes, including untracked files
- have no local commits
- be able to fast-forward to `origin/master`

Gripi restarts itself only when it was started with `bin/start` or `mise run start`. Otherwise, it stops after updating, and you must start it again.

## Gateway state

Gripi stores its own data separately from Pi’s. Each location can be changed with the listed variable:

| Default location | Contents | Variable |
| --- | --- | --- |
| `~/.config/gripi/pinned-dirs` | Pinned session directories | `GRIPI_SESSION_CWDS_PATH` |
| `~/.pi/gripi/browser-access.json` | Approved browsers and access requests | `GRIPI_BROWSER_ACCESS_PATH` |
| `~/.pi/gripi/workspace-access.json` | Approved user tokens | `GRIPI_WORKSPACE_ACCESS_PATH` |
| `~/.pi/gripi/workspace-secret` | Key that links user tokens to users; deleting it disconnects every user from their sessions | `GRIPI_WORKSPACE_SECRET_PATH` |
| `~/.pi/gripi/session-owners.json` | Session owners in multi-user mode | `GRIPI_WORKSPACE_OWNERSHIP_PATH` |
| `~/.pi/gripi/read-state.json` | Read markers | `GRIPI_READ_STATE_PATH` |
| `~/.pi/gripi/pinned-sessions.json` | Pinned sessions | `GRIPI_PINNED_SESSIONS_PATH` |
| `~/.pi/gripi/session-tags.json` | Session tags | `GRIPI_SESSION_TAGS_PATH` |
| `~/.pi/gripi/environment.json` | Saved [environment variables](#environment-variables); contains secrets in plain text, so do not share it | `GRIPI_ENVIRONMENT_PATH` |
| `~/.pi/gripi/attachments/` | Uploaded attachments | `GRIPI_ATTACHMENTS_ROOT` |
| `~/.pi/gripi/web-push-vapid.json` | Web Push keys | `GRIPI_WEB_PUSH_VAPID_PATH` |
| `~/.pi/gripi/push-subscriptions.json` | Web Push subscriptions | `GRIPI_PUSH_SUBSCRIPTIONS_PATH` |
| `~/.pi/gripi/restart-request` | Restart signal for `bin/start` (not read from the env file) | `GRIPI_RESTART_PATH` |
| `~/.pi/gripi/gripi.sock` | Socket for the [`gripi` command](../README.md#command-line), which must run with the same value (not read from the env file) | `GRIPI_SOCKET_PATH` |

If a file is malformed, Gripi leaves it untouched instead of replacing it. Requests that depend on it fail, and the gateway log names the file. To recover, stop the gateway, back up the file, then fix it or move it aside. Moving a file aside resets only its own data, such as approvals or read markers. Pi’s session files are not affected.

## Parallel development instances

A second gateway can read the same Pi sessions, but it must not change a session that another gateway or Pi process is using. Give it its own port and its own paths for every file in [gateway state](#gateway-state), and only change sessions dedicated to that instance.
