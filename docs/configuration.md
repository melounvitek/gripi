# Configuration

Gripi reads settings from `~/.config/gripi/env`, one `NAME=value` per line; set each variable only once. Variables set in the process environment override the file. Restart the gateway after changing a setting. Restarting stops any running Pi work.

Boolean settings accept `1`, `true`, `yes`, or `on` for true and `0`, `false`, `no`, `off`, or an empty value for false, in any letter case. Any other value stops the gateway at startup, so a typo cannot silently change its behavior.

## Server address

The gateway listens on `127.0.0.1:4567`, so only the same machine can reach it. To change this, set `GRIPI_HOST` and `GRIPI_PORT` in the command or the [systemd unit](examples.md#keep-the-gateway-running-with-systemd). Gripi does not read them from `~/.config/gripi/env`:

```sh
GRIPI_HOST=100.x.y.z GRIPI_PORT=4568 ~/.local/share/gripi/bin/start
```

Gripi rejects plain HTTP from other machines. For remote access, prefer HTTPS through [Tailscale Serve](examples.md#https-through-tailscale-serve) or another trusted private reverse proxy.

To allow a [direct VPN connection](examples.md#direct-vpn-connection) over plain HTTP, set:

```sh
GRIPI_ALLOW_INSECURE_REMOTE_HTTP=1
```

Do not use this setting for ordinary LAN or Wi-Fi access. Avoid binding to `0.0.0.0` or `::` unless network access to the machine is already restricted. If you do, list every hostname or IP address that clients use in `GRIPI_PERMITTED_HOSTS`.

## Reverse proxy

Gripi accepts requests only for the hostname or IP address it listens on. When a reverse proxy, such as Tailscale Serve, uses another name, list that name and let Gripi trust the proxy’s headers:

```sh
GRIPI_PERMITTED_HOSTS=gateway.example.ts.net,gripi.example.net
GRIPI_TRUST_PROXY_HEADERS=1
```

`GRIPI_PERMITTED_HOSTS` is a comma-separated list of hostnames, IPv4 addresses, or bracketed IPv6 addresses. Ports are allowed but ignored when matching.

Only enable `GRIPI_TRUST_PROXY_HEADERS` when all traffic goes through a trusted private proxy that overwrites the `X-Forwarded-Proto`, `X-Forwarded-Host`, and `X-Forwarded-Port` headers. If clients can reach the gateway without the proxy, they can fake these headers. Leave it off for direct localhost, LAN, and VPN connections.

If a request uses a hostname that is not configured, Gripi blocks it and shows the setting to add. Follow that advice only if you recognize the hostname as your Gripi address.

The gateway accepts request bodies up to 64 MiB; this limit is fixed. Set the same or a lower limit in your proxy, and do not let the proxy buffer request bodies without a limit.

## Access approval

In single-user mode, every new browser must be approved once. The access page offers two options:

- Enter the admin password.
- Select **Ask access**. The page shows a code, and browsers that are already approved show a prompt with **Allow** and **Deny**. Allow only if the code matches the one on the new device.

Approval is saved per browser and address, so the desktop app and each URL, such as `localhost` and a `ts.net` name, are approved separately.

The admin password is `GRIPI_ADMIN_PASSWORD` in `~/.config/gripi/env`. The gateway does not start without it unless approval is disabled. The installer generates it, and `~/.local/share/gripi/bin/gripi-password` adds one if it is missing. To change it, edit the file and restart the gateway. Browsers that are already approved stay approved, so if the password leaks, also remove browsers you do not recognize.

Approved browsers are listed under `approved_browsers` in `~/.pi/gripi/browser-access.json`, with their approval time and user agent. To remove a browser, delete its entry. The change applies to the browser’s next request.

### Disabling approval

```sh
GRIPI_BROWSER_AUTH_DISABLED=1
```

This lets anyone who can reach the port use Pi on the gateway machine. Only use it when localhost, a VPN, firewall rules, or another private network boundary already limits access to trusted devices and users.

## Multi-user mode

By default, Gripi shows all Pi sessions to a single trusted user. To give each user a private session list, enable multi-user mode:

```sh
GRIPI_MULTI_USER_MODE=1
```

Each user generates a private user token and sees only their own sessions. The same token shows the same sessions in any browser. Tokens cannot be recovered, so users must store them safely. Sessions created before multi-user mode was enabled, or in Pi CLI, have no owner and are not shown to anyone until a user claims them with `gripi claim`.

User-token approval replaces browser approval:

- The first user is created with the admin password.
- Later users generate a token and select **Ask for access**. An approved user then approves the request.

Approved users are listed under `approved_workspaces` in `~/.pi/gripi/workspace-access.json`. Entries contain an ID derived from the token, not a name. To find a user’s ID, look up one of their session files in `~/.pi/gripi/session-owners.json`; delete the matching entry to revoke access. The user’s saved [environment variables](#environment-variables) stay in `~/.pi/gripi/environment.json` under the same ID until you delete them there. With `GRIPI_BROWSER_AUTH_DISABLED=1`, every new token is approved automatically and stays approved until it is removed from that file. Only use that combination when every client that can reach the gateway is trusted.

Multi-user mode separates session lists and [environment variables](#environment-variables), not permissions: all users run commands as the same OS user and share settings such as the selected model and thinking level. For the same reason, one user’s variables are not secret from the others.

The session commands of the [`gripi` command](../README.md#command-line) act for the user whose token is in `GRIPI_USER_TOKEN`, and reach only that user’s sessions. In a terminal, set it to your user token. Pi in a user’s session gets one automatically, so agents can run the commands without setup. That token works only for these commands, not in a browser, so it does no harm when Pi shows its environment to the model. `gripi claim` with the full ID of a session that has no owner, such as one from Pi CLI, makes the session yours; a session another user owns cannot be claimed.

## Environment variables

Gripi can save environment variables for Pi, for example your own [GitHub](#github) token on a shared gateway. Pi and every command it runs get them on top of the gateway’s environment, and a saved variable replaces a gateway variable of the same name.

The gateway’s own settings are not passed on. Pi gets no `APP_ENV` and no `GRIPI_*` variable from the gateway, so the projects it works on, and a gateway started from a session, do not inherit them. The exceptions are `GRIPI_SOCKET_PATH`, which the [`gripi` command](../README.md#command-line) needs to reach this gateway from inside a session, and the `GRIPI_E2E_*` variables of the [browser tests](testing.md#external-implementation). In [multi-user mode](#multi-user-mode), Pi also gets a `GRIPI_USER_TOKEN` of the session’s owner for the same command. To give Pi an `APP_ENV` of its own, add it to the saved variables.

Edit them in the Environment dialog, opened with the key icon in the sidebar header or **Environment…** in the Ctrl+K palette. The list shows names only; a value is shown only while its row is open for editing. Pasting several `NAME=value` lines adds them at once, and lines starting with `#` are ignored.

In single-user mode, the variables apply to every Gripi session. In [multi-user mode](#multi-user-mode), each user has their own set, applied only to the sessions that user owns. A session with no owner gets none. Variables saved in one mode are not used or shown in the other, but they stay in the file.

A change applies from the next message or `!` command in each session. If the session’s Pi process is idle and started before the change, Gripi restarts it first, which loses process-only state in the same way as [stopping an idle process](#pi-process-lifetime). A running turn keeps the old values until it ends, and so do messages steered or queued during it.

A new session that Pi has not saved yet exists only in its Pi process, so Gripi starts it again in the same folder and under the same path, with the model, thinking level and name chosen in it so far. Nothing else carries over: the output of `!` commands run in it before the change leaves Pi’s context, and a session forked from its first message loses its link to the session it came from. If the new Pi process refuses the chosen model, for example because its API key is gone, the message fails with Pi’s reason and the session keeps the old values. Pi CLI in a terminal does not get the variables; `gripi send` does, because it goes through the same path as a message from the browser.

Names consist of letters, digits, and `_`, and cannot start with a digit. `HOME`, `GRIPI_*`, and `PI_CODING_AGENT_*` are refused, because they move Gripi’s or Pi’s directories. A value cannot be empty and is at most 16 KiB long. Each user can save at most 100 variables.

The values are stored as plain text in `~/.pi/gripi/environment.json`, which only the gateway’s OS user can read; nothing Pi-owned changes. In multi-user mode, the variables separate identity, not secrets: every user runs commands as that OS user, so one user’s Pi can read the file with another user’s values. For real separation, run one gateway per OS user.

### GitHub

The main use is acting as yourself on GitHub from a shared gateway. `GH_TOKEN` alone only changes `gh`: pull requests, issues, and API calls. Commits and `git push` still use the gateway’s identity unless your name, email, and git configuration are set too.

**+ add GitHub variables** in the dialog opens the whole set, with the first five values empty:

```txt
# gh: pull requests, issues, API
GH_TOKEN=
# your name and email on commits
GIT_AUTHOR_NAME=
GIT_AUTHOR_EMAIL=
GIT_COMMITTER_NAME=
GIT_COMMITTER_EMAIL=
# git push over HTTPS with your token, also for SSH remotes; leave as is
GIT_CONFIG_COUNT=2
GIT_CONFIG_KEY_0=url.https://github.com/.insteadOf
GIT_CONFIG_VALUE_0=git@github.com:
GIT_CONFIG_KEY_1=credential.https://github.com.helper
GIT_CONFIG_VALUE_1=!gh auth git-credential
```

Fill in the empty values and save:

- `GH_TOKEN` is your GitHub token, used by `gh`. Create it at <https://github.com/settings/tokens>. For a classic token, `gh` asks for at least the `repo`, `read:org`, and `gist` scopes.
- The `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables put your name and email on commits.
- The `GIT_CONFIG_*` variables make git reach GitHub over HTTPS and ask `gh` for the token, so pushes to `git@github.com:` remotes use your token too. They need `gh` installed on the gateway machine. Remotes written as `ssh://git@github.com/…` are not covered and would need one more key and value pair.

On the gateway machine, `gh` must be the only credential helper git uses for GitHub. Make it so by running this once as the gateway’s OS user:

```sh
gh auth setup-git --hostname github.com --force
```

If git also uses another helper there, such as the macOS keychain or `store`, a login saved in it is used instead of your token, and a successful push saves the pushing user’s token in it for everyone.

If `GH_TOKEN` is saved without the rest, the dialog warns that commits and `git push` still use the gateway’s identity and offers **+ add the rest for GitHub**.

## Running commands as root

Agents in Gripi can’t use `sudo` when it asks for a password, because nothing can type it. Instead, an agent in a Pi or Hermes session can run `gripi sudo -- <command>`. Gripi then shows the exact command and its directory in place of that conversation’s editor and asks for your password. **run as root** runs the command with sudo, and the agent gets only its output and exit code. **cancel**, or 2 minutes without an answer, refuses it. The password goes from the browser to the gateway’s memory and, only if sudo asks for it, to sudo. It never reaches the agent, the model, or any file.

Gripi leaves plain `sudo` as it is, so it still fails there. `gripi sudo` is Gripi’s own: Pi CLI in a terminal shows no prompt for it.

Agents don’t know about it until you tell them. For Pi, add a line to `~/.pi/agent/AGENTS.md`:

```md
- To run a command as root, use `gripi sudo -- <command>`, not `sudo`; I enter the password in Gripi. See `gripi help sudo`.
```

For Hermes, add it to the hint for ACP clients in `~/.hermes/config.yaml`, in the same string as any [`MEDIA:` hint](#hermes-agent-experimental). Editors that use Hermes get it too, but `gripi sudo` fails there:

```yaml
platform_hints:
  acp: "To run a command as root, use `gripi sudo -- <command>`, not `sudo`; the user enters the password in Gripi."
```

Requirements and limits:

- Linux only, tested with [sudo-rs](https://github.com/trifectatechfoundation/sudo-rs). Gripi answers only pam_unix’s untranslated `Password: ` prompt. If PAM asks for anything else, such as a one-time code, or in another language, sudo fails without running the command.
- sudoers must not keep `SUDO_ASKPASS` or `GRIPI_SUDO_TOKEN` with `env_keep`, which would pass them on to the command.
- Every command needs your approval and your password. Gripi runs sudo with `-k`, so an earlier sudo login doesn’t count.
- `!` commands and nested subagents can’t use it. Gripi can’t tell which conversation they belong to, so `gripi sudo` fails at once.
- Hermes stops a terminal command after 180 seconds unless its model sets a longer timeout, and the wait for your answer counts.
- In [multi-user mode](#multi-user-mode), only the session’s owner sees the request and can answer it.

This keeps the password from leaking by accident. It doesn’t protect against a hostile agent: one that runs as the gateway’s OS user could replace Gripi, or ask you to approve a harmful command. Read the command before you run it, because it runs as root.

## Pinned session directories

List frequently used directories in `~/.config/gripi/pinned-dirs` to keep them available in the New Session dialog:

```txt
/home/alice/projects/gripi
/home/alice/projects/another-project
```

Use one directory per line. Blank lines and `#` comments are ignored.

## Session tags

Add tags with the tag icon in the conversation header, **Tags…** in a session’s menu, or [`gripi tag`](../README.md#command-line). Select a tag in the sidebar to filter by it; pinned sessions stay visible. Forks and clones keep their tags.

Tags are lowercased, up to 64 characters long, and limited to 32 per session. They are stored in `~/.pi/gripi/session-tags.json`, not in Pi’s session files, and are private to each user in multi-user mode.

## Project resource approval

Gripi starts Pi with `--approve`, so project-local settings, extensions, skills, prompts, themes, system prompts, and packages load without asking. Pi CLI asks before trusting a project. Project extensions and package installation scripts can run any code as the gateway OS user, so only open projects you trust.

To turn automatic approval off:

```sh
GRIPI_AUTO_APPROVE_PROJECTS=0
```

Pi then applies its normal trust rules, including saved trust decisions and the global `defaultProjectTrust` setting. Gripi cannot show Pi’s trust prompt, so with the default `"ask"` setting, project resources stay disabled until you trust the directory in Pi CLI. Gripi never changes Pi’s saved decisions in `~/.pi/agent/trust.json`.

## Custom Pi runtime

By default, Gripi runs `pi` from `PATH`. To use specific executables, set both variables:

```sh
GRIPI_NODE=/path/to/node
GRIPI_PI=/path/to/pi
```

The selected runtime must already work, authenticated and configured, for the gateway’s OS user.

## Hermes Agent (experimental)

Gripi can also talk with [Hermes Agent](https://github.com/NousResearch/hermes-agent) in a panel next to Pi's sessions. It is off unless you name the Hermes to run:

```sh
GRIPI_HERMES=/home/me/.local/bin/hermes
```

The path can also be a Hermes profile wrapper, which `hermes profile alias <name>` creates, to run that profile with its own sessions, memory and model. Gripi runs `<path> acp`, Hermes's Agent Client Protocol server, so that Hermes must already work and be authenticated for the gateway's OS user. Gripi doesn't install, configure or update Hermes, and `gripi check` checks it too once it is set.

With Hermes on, the Hermes tab on the window's right edge opens and closes the panel, as do Ctrl+H and `hermes` typed in the Ctrl+K palette. The panel stays put while you switch sessions. On a wide screen it takes a column of its own, and on a narrower one it lies over the conversation, with the tab on its edge. With the panel open, Tab goes from a composer to its conversation and then on to the other side's composer. On a phone it fills the screen, and on a touch screen `‹ Gripi` closes it instead of `×`. `↗` opens it in a window of its own.

The panel holds one conversation for quick questions, not sessions: `new` starts over, and every panel, window and device shows the same conversation. If Hermes replies after you close the panel, the tab's line turns orange. Gripi forgets the conversation when it restarts, and Hermes's conversations never show in the sidebar. Hermes still keeps them in its own database, and `gripi list` lists them. A conversation belongs to no project: it always runs in your home folder.

What to expect:

- Gripi lists only the Hermes sessions that ACP clients created, such as Gripi itself or an editor. Hermes's CLI, desktop app, cron jobs and messaging platforms keep their sessions to themselves.
- All Hermes sessions run in one Hermes process. Gripi starts it only for the Hermes panel and `gripi` commands, which then wait a few seconds, and it stops once nothing has used it for the [Pi process lifetime](#pi-process-lifetime).
- While Hermes works, the composer waits: Stop is the only action. Gripi doesn't choose Hermes's model yet, and `gripi open` refuses Hermes's sessions.
- A message to Hermes takes up to about 36 MB of images, which Hermes reads encoded on one line of at most 50 MB.
- Hermes shares a file by writing `MEDIA:` and the file's absolute path in its reply. Gripi shows a PNG, JPEG, GIF or WebP image of up to 10 MB in place of the tag, for as long as the file exists. It leaves tags in code blocks and quotes, tags of other files, and the tags of a reply that has nothing else to say as they are. Hermes tells its model about the tag only in its screenshot tool, unless `~/.hermes/config.yaml` does so for every ACP client, which editors then show as plain text:

  ```yaml
  platform_hints:
    acp: "You can send files natively: write MEDIA:/absolute/path/to/file in your response."
  ```

- Hermes asks before dangerous commands, as its `approvals.mode` setting says, and before editing sensitive files such as `.env` or keys. The question appears as a dialog in the panel. Other edits go ahead without asking, as in Hermes's CLI. A dialog stays open after Hermes has stopped waiting for the answer, after its `approvals.timeout`, until you close it.
- A session that another ACP client, such as an editor, continues keeps showing what Gripi's Hermes loaded, until that Hermes restarts.
- Saved [environment variables](#environment-variables) reach Hermes when it starts. After a change, Hermes restarts with them before the next conversation starts, once no other Hermes session is open. A new conversation's first message still runs with the variables from before, because the conversation lives only in the running Hermes until then.
- After `hermes update`, Gripi restarts its Hermes before a conversation starts or opens, unless Hermes is replying. It compares the first line of `<path> --version`. A message sent right after that into another open conversation fails once, and sending it again works. A new conversation without a message is gone, as when Hermes stops.
- [Multi-user mode](#multi-user-mode) refuses the setting, because every user would share the one Hermes, with its memory, skills and messaging accounts.

### Voice conversations

You can talk with Hermes: Gripi listens, sends what you say as a message, and reads Hermes's reply aloud. It uses Hermes's own speech recognition and voice, which the `stt:` and `tts:` settings in Hermes's `config.yaml` choose, and reaches them through Hermes's dashboard, which `hermes dashboard` or `hermes serve` runs. Voice is on when Gripi knows the dashboard's address, username and password:

```sh
GRIPI_HERMES_DASHBOARD_URL=http://127.0.0.1:8787
GRIPI_HERMES_DASHBOARD_USERNAME=me
GRIPI_HERMES_DASHBOARD_PASSWORD=...
```

Gripi logs in with the dashboard's password login, its `basic` provider, which `dashboard.basic_auth` in Hermes's `config.yaml` sets up. The dashboard asks for a login only when it listens on more than localhost or has a `dashboard.public_url`; otherwise Gripi can't use it. Only the gateway talks to the dashboard, never the browser.

Browsers allow the microphone only over HTTPS or on `localhost`, so other devices need [HTTPS](examples.md#https-through-tailscale-serve).

The waveform button next to ＋ in the Hermes panel's composer starts a voice conversation, which takes the place of the panel's messages until it ends: bars follow your voice and Hermes's, with the sentence Hermes is speaking underneath. In the conversation, what you said shows as bars too; tap them to read the transcript. Pause to send what you said; if you go on talking before Hermes gets it, the rest joins the same message. Quiet blips play until Hermes's reply starts. Talk over a reply to interrupt it, or over Hermes's work to stop it and send what you said instead; noise without words leaves Hermes working. Saying “stop” finishes the conversation without stopping Hermes; `end` finishes it at any time, and Stop still stops Hermes. `mute` stops listening, though what you said just before is still sent. Ctrl+Shift+H starts and ends a voice conversation, and Ctrl+Shift+M mutes it, also from the session while the panel is open.

## Workers

A worker is another computer that runs chosen sessions for the gateway, which [`gripi worker`](../README.md#workers) adds and moves sessions to. Main, here, is the gateway’s machine. A session moves alone, on a private copy of its repository on the worker, while the repository’s other sessions keep running on main, and what it changed there comes back when it returns. Main keeps the interface, Gripi’s settings, and a copy of what each session on a worker changed and of its session’s file, which follow the worker’s. Gripi reaches a worker only with main’s `ssh`, as the gateway’s OS user and with that user’s SSH configuration.

### Setting up a worker

The worker needs:

- Linux on the same architecture as main, which must run Linux too.
- Pi 0.99.0 or later on main. Gripi copies main’s Pi to the worker, and refuses to connect to a worker with an older one.
- A systemd user manager with cgroup v2. Gripi runs its helper there with `systemd-run --user`, which lets it stop everything that a session started.
- Git, and the tools that the projects need, on the `PATH` of the user’s login shell. Gripi brings only Node and Pi.
- Unprivileged user namespaces, always: each moved session runs in a private view of its copy (see [moving a session](#moving-a-session)), also when the worker user’s home folder has main’s path, and everything runs in a private view of that home folder when it has another path than the gateway user’s on main (see below). Arch, Fedora and Debian allow them. Ubuntu 23.10 and later block them with AppArmor; allow them with `sudo sysctl kernel.apparmor_restrict_unprivileged_userns=0`, and put `kernel.apparmor_restrict_unprivileged_userns=0` in a file in `/etc/sysctl.d/` to keep that after a restart.
- Logins from main’s `ssh` without a prompt: run `ssh user@host` once to accept the host key, and `ssh-copy-id user@host` to log in with a key. The gateway runs `ssh` too, so a key with a passphrase needs an agent that the gateway’s environment reaches through `SSH_AUTH_SOCK`. sshd on the worker must allow forwarding TCP ports and Unix sockets (`AllowTcpForwarding` and `AllowStreamLocalForwarding`) and at least 8 sessions per connection (`MaxSessions`), as it does by default.

In practice, give Gripi a dedicated user on the worker, with any name and home folder, such as one that `useradd -m gripi` makes. Everything that the sessions run, runs as that user.

Pi’s sessions name the paths of the projects and of Pi’s agent folder, so sessions on the worker use main’s paths. When the worker user’s home folder has another path than the gateway user’s on main, everything that Gripi runs there with main’s paths, such as Pi with everything it starts and the copies of main’s files, runs in a private view of the worker’s files: main’s home folder, such as `/home/alice`, shows the worker user’s home folder, such as `/home/gripi`. A user of the worker whose home folder has main’s path is never touched. Everything else stays as it is, such as `/tmp`, `/usr`, `/srv`, and what is next to main’s home folder, such as `/home/projects` or the other users’ home folders, which stay as private as they are. The view shows what was next to main’s home folder when the gateway connected to the worker: a folder made there later is missing from it until the gateway connects again, such as after a restart. Nothing new can be made directly in the folder that holds main’s home folder, such as `/home`, because the view would lose it. The folder that holds main’s home folder, such as `/home`, must exist on the worker, and main’s home folder must not be directly in `/`, as `/root` is.

In the view:

- Tools see the worker’s user as itself, with `HOME` set to main’s home folder, and the files that they write belong to it.
- Programs that need setuid don’t work, such as `sudo`, and rootless Podman, which needs `newuidmap`.
- Services that the worker user’s systemd starts, such as with `systemd-run --user` without `--scope`, run outside the view and don’t see main’s paths. They run as the worker’s user, so they can’t change other users’ files either.
- Docker works: each moved session gets a Docker socket of Gripi’s own in `DOCKER_HOST`, in place of main’s, which passes its requests on to the worker’s Docker, as `DOCKER_HOST` in the worker user’s systemd environment (not its login shell’s), the current Docker context or `/var/run/docker.sock` names it. The Docker daemon runs outside the views, so the socket changes the paths where requests name host folders, in bind mounts of new containers and in local volumes bound to a folder: paths in the folders that show the session’s copy, such as `~/Work`, to the copy, and other paths in main’s home folder to the worker user’s home folder. It first follows the symbolic links in those paths as the sessions see them, because the daemon would follow them outside the view, where main’s home folder may be another user’s, and refuses a path whose links it cannot follow, such as a link to a missing path. It doesn’t change them in Swarm services, and it cannot reach Docker over `ssh://` or over `tcp://` with TLS, so with such an endpoint, Docker fails in the sessions.

Membership of the `docker` group makes the worker’s user root on the worker in effect, and containers can leave files owned by root in the projects; rootless Docker avoids both. So the Docker socket only prevents accidents: sessions can still reach other users’ files through Docker on purpose.

Gripi’s helper runs under the worker user’s systemd, which keeps the groups that it started with. So after `sudo usermod -aG docker gripi`, restart it with `sudo systemctl restart user@$(id -u gripi).service`, which stops everything that the user runs there, sessions included.

Then add the worker on main:

```sh
gripi worker add gripi@beelink.example.ts.net
```

`add` checks the system, Git and systemd, installs Gripi’s helper there and checks that it can make private views, also when the worker user’s home folder has main’s path, saying what to do when the system blocks them. It fails when the worker’s user cannot create Pi’s agent folder at its path on main, as the sessions there see it, or when the worker shares main’s files, as main itself as the same user or a home folder mounted on both would: the worker’s files would replace main’s, such as Pi’s logins. Main checks both again whenever it connects. A worker that is main as another user is fine, because the sessions there see that user’s home folder at main’s. The worker is named after the first part of the host name, `beelink` here, unless `--name` names it. `gripi worker list` lists the workers.

`add` also checks, under the worker user’s systemd as the helper runs, whether the worker’s user can use the worker’s Docker. When the worker has Docker but its user can’t use it, `add` still adds the worker, and says why and what an admin of the worker can do. Main checks Docker again whenever it connects, says what it found in the gateway’s log when the sessions can’t use Docker, and **Run on worker…** shows it for the chosen worker, once main has connected to it.

### What a worker gets

The first time a session or a move needs a worker, main connects to it. On every connection, it brings the worker up to date, sending only what changed:

- Gripi’s own executable, as the helper that runs the sessions, and Node and the Pi package at main’s versions, in `~/.local/share/gripi/worker` on the worker. Pi there has `node`, `pi` and `gripi` on its `PATH`.
- Pi’s agent folder, with everything in it, such as settings, models, extensions, skills, prompts and installed Pi packages, but without `auth.json`, `mcp-auth.json` and the sessions. Links in it to files elsewhere, such as a folder of your own settings, are copied as the files they point to. Other files that Pi’s settings name, such as a package loaded from a local folder, are not copied.
- Gripi’s Pi extensions, at their paths on main.

Later changes to Pi’s configuration on main reach a worker the next time main connects to it, such as after the gateway restarts. Logins follow at once:

- The worker’s `auth.json` has main’s API keys as they are, and main’s OAuth logins with their access tokens but without their refresh tokens. Some providers’ refresh tokens work only once, so two machines that refresh the same login revoke it on both.
- Only main refreshes logins. About 15 minutes before a token expires, or halfway through a shorter token’s life, main has its own Pi refresh the login with `pi auth print-bearer-token`. Main checks its `auth.json` and `models.json` every few seconds and gives connected workers what changed; Pi there picks it up without a restart. Gripi only reads main’s `auth.json`.
- Keys that Pi gets by running a command, `!command` in `auth.json` or `models.json`, are resolved on main with `pi auth print-api-key`, because the command may read files that only main has. A key that main cannot resolve, such as from a locked password store, is left out, with a warning in the gateway’s log, and main tries again a minute later.

Pi on a worker gets the environment variables that it gets on main, including the saved [environment variables](#environment-variables), except those that describe main, such as `HOME`, `USER`, `SHELL`, `SSH_*`, `XDG_*`, and the terminal’s and the desktop’s. Its `PATH` is the worker user’s login `PATH`, with the `bin` folder of Gripi’s files first.

Every `localhost` port in the URLs of Pi’s `models.json` and `mcp.json`, such as a local model proxy or an MCP server, reaches the same port on main from the worker while main is connected to it. A port that cannot be forwarded, such as one that something on the worker uses, keeps main from connecting.

A `gripi` socket of the worker’s own is forwarded to the path of main’s socket on the worker, so the [`gripi` command](../README.md#command-line) works in sessions there. It reaches only the sessions on that worker, and refuses `gripi sudo`, `gripi claim` and new sessions, which would start on main.

### Moving a session

`gripi worker move <session> <worker>`, or **Run on worker…** in the Ctrl+K palette, moves one session to the worker. Only that session moves: the repository’s other sessions keep running on main. It runs there on a private copy of its repository, which no other session uses, and **Run on worker…** lists what the copy gets before it moves:

- the repository’s Git folder, with all its branches, tags and stashes;
- the worktree that the session started in, and the worktrees that its tool calls named, such as the files that it read or edited and the folders of its shell commands; the repository’s other worktrees stay on main only;
- in those worktrees, the tracked and untracked files, and Git-ignored files of up to 10 MB, such as `.env` or `config/master.key`.

Ignored folders, such as `node_modules/` or `tmp/`, aren’t copied from main. The copy takes them from the worker’s latest earlier copy of the repository, or else from the ignored folders that its deleted copies left, at the same paths, sharing their contents where the file system can (`cp --reflink=auto`). So install the dependencies on the worker once. They never come back to main.

On the worker, the folders directly in main’s home folder that hold the repository and those worktrees, such as `~/Work`, show the session’s copy: there, the session sees only its repository, not the other projects in `~/Work`. Everything else in the home folder, such as Pi’s configuration, toolchains and caches, is the worker user’s, as for any session there. Two sessions of one repository can run on one worker, each on its own copy.

A session can’t move while it works. Nor can it move when its folder isn’t in a Git repository; when the repository is bare, or its Git folder or those worktrees aren’t in main’s home folder; or when the folders that would show the copy hold Pi’s agent folder, Pi’s sessions, Gripi’s own folders or the session’s file, which the copy would hide. **Run on worker…** says so before it moves. A repository with submodules, Git LFS or alternates, or with a merge, rebase, cherry-pick or revert in progress, can’t move either; the move fails with the reason once it has waited for the other sessions.

#### Waiting for the other sessions

Main takes the base of the move, the state of the repository’s files, refs, checkouts and stashes from which the copy starts, once the repository’s other sessions on main are idle: it waits until they have finished their steps, `!` commands, compactions and queued prompts, for up to three minutes, and holds the new prompts that they get meanwhile. The session’s page says which session it waits for. Then the session’s own Pi stops, main takes the base, and the other sessions go on. A return waits the same way, and holds the other sessions’ new prompts until it has brought the changes to main’s folders. When a session doesn’t finish in time, the move or return fails and asks to try again.

A new session that Pi has not saved yet exists only in its Pi, so it starts again on the worker as after a change of the [environment variables](#environment-variables), and a return does the same on main. If it cannot start, or not with what was chosen in it, the move or return fails with the reason, and the session starts again with what was chosen in it at its next return.

Gripi cannot tell when something outside Gripi, such as your editor or Pi CLI, changes the repository’s files, so it doesn’t wait for that. A file saved while main takes the base may reach the copy half-written. A return compares main’s files with what it expects before it changes them, but a change saved while it brings the session’s changes in can be lost. So avoid editing the repository’s files yourself while a session moves or returns.

#### On the worker

From then on, the session runs on the worker, and so does everything that its Pi starts: tools, `!` commands, subagents and Docker. Worktrees that it makes in the folders that show its copy, such as in `~/Work`, join the copy. Files outside the copy, such as in `/tmp`, exist only on the worker, and so do the files of worktrees that it makes there. Only the moved session shows the worker: its name and state are in the session’s header and in the editor’s footer, with the ports that main forwards for it, and its row in the sidebar has the worker’s icon.

Pi there loads a second Gripi extension, which holds each tool result and `!` command until main has the changes it made, usually a fraction of a second. If main cannot confirm them, or not within a minute, the result becomes an error that says that the changes may be missing on main, and the session’s next tool calls fail until main’s copy follows again. A file in the copy that the worker cannot read, such as one without read permission, also stops confirmations until the worker can read it. Main keeps its copy of the session’s changes in `moves/<move>/` in Gripi’s state folder, not in the repository’s folders, which the repository’s other sessions keep using, and the session’s file at its path. While the session is on the worker, refs under `refs/gripi/moves/<move>/` in the repository keep its base from Git’s garbage collection.

### Coming back

`gripi worker return <session>`, or **Continue on main** in the palette, brings the session back. It waits for the repository’s other sessions as a move does, stops everything that the session runs on the worker, including background processes, takes its last changes, and brings them to main’s folders. For each file, ref and checkout, it compares the copy and main now with the base:

- What only the session changed comes back: files, with their type and mode, new and moved branches and tags, stashes that it added, and worktrees that it made, which main makes with `git worktree add`. Git objects are only added to main’s repository.
- What only main changed stays.
- A text file that both changed comes back merged, with `git merge-file`, when their changes don’t overlap.
- Otherwise main keeps its own version, and the worker’s is kept aside: a file that both changed in overlapping lines, a binary file or a link that both changed, a file whose type changed, or that one side deleted and the other changed; a branch or tag that both moved, or that main checks out in another worktree; and a worktree that the session made at a path that main uses.
- The session’s checkout of a worktree, its branch or HEAD and its index, comes back only when main’s checkout and files there are still as they were at the base, and Git rebuilds the index. Otherwise main keeps its own, and the worker’s is kept aside.
- Main keeps its Git configuration and hooks, and the stashes and worktrees that the session dropped or removed; the worker’s changes to them are listed with what was kept aside.

Main never gets conflict markers, and Gripi never merges or rebases history. Returns of one repository run one at a time, and a return that stops, such as when the worker can’t release the session or the gateway restarts, finishes when it runs again; until then, the session doesn’t start, and its page offers **continue on main**. The worker deletes its copy once main has the changes, and keeps its ignored folders for the repository’s next copies.

What a return kept aside stays in a recovery folder, `returns/<move>/` in Gripi’s state folder, and under recovery refs in the repository:

- For a file kept aside, `worker/`, `base/` and `main/` in the folder hold the worker’s, the base’s and main’s version, at its full path, such as `returns/<move>/worker/home/alice/Work/shop/src/cart.ts`; a side that deleted the file has none. Compare them with `diff`, or merge the worker’s changes into main’s file, with conflict markers where they clash, with `git merge-file <main’s file> <the base’s> <the worker’s>`. The worker’s changed Git configuration and hooks are only in `worker/`.
- The worker’s commits that main didn’t take are under `refs/gripi/returns/<move>/`, by their names, such as `refs/gripi/returns/<move>/refs/heads/feature` for the worker’s branch `feature`. See them with `git log feature..refs/gripi/returns/<move>/refs/heads/feature`, and keep them with `git branch feature-worker refs/gripi/returns/<move>/refs/heads/feature`, a merge or a cherry-pick.
- For a checkout that main kept, the worker’s index is listed in `worker/<the worktree’s Git folder>/index.txt`; for a worktree that main didn’t make, its files are in `worker/<its path>`.

The session’s page lists above the editor what was kept aside and where, with each item’s reason in its details, until you dismiss that notice, which deletes the recovery folder and the refs, after asking. So copy what you need first. A return that kept nothing aside leaves nothing behind and shows no notice.

### Losing a worker

The helper pings main every second. When main has not answered for 30 seconds, or at once when the connection closes, it stops Pi and everything that Pi started on the worker. Main treats the worker as unreachable when it has had no ping to answer for 15 seconds, or when the connection ends. The step that each session there was running then ends with an unknown outcome, because nobody knows whether it finished, and its tool block says so. Main has each session up to the entries that reached it, and its changes as they were after the last tool result that main confirmed.

What happens next is up to you:

- If the worker answers again, the session’s next message connects again and continues on the worker, from its copy there.
- Otherwise, continue on main. In the editor’s place, Gripi counts down to when the worker must have stopped everything, 32 seconds after main’s last answer, and then offers **continue on main**; `gripi worker return` refuses until then and says when that is. The session’s changes then come back as main last got them, as in a return. The worker’s copy may have changes that main never got; the worker deletes it once main reaches the worker again.

Losing a worker loses the running step and the background processes that the session started there, such as dev servers, which, unlike on main, stop with the connection. Continuing on main also leaves the files outside the copy behind on the worker. Stopping the gateway, such as for an update, also stops everything that sessions run on workers.

The helper cannot stop what others run for Pi: Docker and Podman containers, which their daemons own, and anything started with `systemd-run --user`, such as the Pi sessions that the `gripi-orchestrate` skill starts. These keep running after a disconnect or a return, and what they change afterwards stays on the worker, so stop them yourself.

### Forwarding ports

`gripi worker forward <session> <port>`, or **Forward a port…** in the palette, makes a port on the localhost of the worker that runs the session, such as a dev server’s, available on main’s localhost: at the same port, or at the next free one, which it prints. Main listens on localhost only. The editor’s footer shows the ports that main forwards for the session. A forward lasts until `gripi worker unforward` or **Stop forwarding** in the palette, or the session’s return, for every session that asked for it, or until main’s connection to the worker ends; it isn’t restored when main connects again.

### Limits

- Pi’s `mcp-auth.json` isn’t copied, so MCP servers that need an OAuth login are not logged in on workers.
- Main cannot refresh logins of providers that Pi extensions add, so on a worker such a login stops working when its token expires, unless main’s own Pi has refreshed it meanwhile.
- A session on a worker can be deleted only once it continues on main, because the worker would send main its file again. It can’t start a new session in place, with `/new`, `/clone` or `/fork`, nor can `gripi` on the worker.
- Continue a session on a worker only in Gripi. If Pi CLI on main writes it, Gripi asks to take the session over, as for any session in use in Pi CLI, and then shows a conflict, because the worker’s copy replaces what Pi CLI wrote.
- Only the session’s repository is on the worker: other projects in the folders that show its copy, such as another repository in `~/Work` that the session also works in, are missing there.
- Worktrees that the session removes on the worker stay on main. Worktrees that it makes outside the folders that show its copy, such as in `/tmp`, stay on the worker with their files: the commits on their branches come back with the Git folder, but not commits that only a detached HEAD there has.
- Main’s copy of the session’s changes writes each batch of them to a journal before it applies it. When main refuses one of them for good, such as a folder below a symbolic link that the session made, the batch stays in the journal, and main’s copy can’t open until it is applied: the session can neither confirm its tool results nor come back, and recovering from that is a manual repair of `moves/<move>/`.
- Gripi doesn’t wait for edits made outside Gripi while a session moves or returns (see [waiting for the other sessions](#waiting-for-the-other-sessions)).
- The `moves/` and `returns/` folders in Gripi’s state folder must be on the same file system as the repositories and Pi’s sessions.

### Removing a worker

`gripi worker remove <worker>` forgets a worker once no session is on it. Gripi’s files there stay: `~/.local/share/gripi/worker`, with the ignored folders of the repositories that sessions moved with, and the copies of Pi’s agent folder and of the sessions’ files, which are in the worker user’s home folder for those in main’s. Delete them on the worker when you no longer need them.

## Session location

Gripi lists sessions from `~/.pi/agent/sessions`. If Pi stores sessions somewhere else, for example because `PI_CODING_AGENT_DIR` is set, point Gripi there:

```sh
GRIPI_SESSIONS_ROOT=/path/to/sessions
```

## Pi process lifetime

Gripi stops a Pi process about five minutes after the last user action. Background polling from open tabs does not count, so a forgotten tab cannot keep Pi running. Running agent turns, compaction, shell commands, and new sessions that Pi has not saved yet are not stopped for being idle.

Using the session again starts a new Pi process. The conversation is kept in Pi’s session file, but the first response takes longer, and process-only state, such as open extension dialogs, is lost.

```sh
GRIPI_RPC_IDLE_TIMEOUT_SECONDS=300
GRIPI_RPC_IDLE_SWEEP_SECONDS=30
```

The timeout is a whole number of seconds; `0` disables it. The sweep interval sets how often Gripi checks for idle processes and can be any positive number of seconds.

## Web Push notifications

Turn notifications on with the bell icon in the sidebar header, which is orange when they are on and crossed out when they are off or blocked. On iPhone and iPad, this requires iOS/iPadOS 16.4 or newer and Gripi added to the Home Screen.

Gripi sends the notification one minute after a reply finishes, unless the session has been read in any of your Gripi clients or is open and focused in one of them. A client that disconnects stops counting as focused after about 30 seconds.

Web Push requires HTTPS, such as [Tailscale Serve](examples.md#https-through-tailscale-serve). The gateway also needs outbound HTTPS access to the browser’s push service. Delivery is best-effort.

Gripi creates its push keys on first use in `~/.pi/gripi/web-push-vapid.json` and stores subscriptions in `~/.pi/gripi/push-subscriptions.json`. Keep the key file: replacing it breaks existing subscriptions, and every device must turn notifications on again. Both files contain secrets, so do not share them.

The `/notification-test` page registers the current browser and sends a test notification.

## Resource monitoring

On Linux with cgroup v2, Gripi can show RAM and CPU usage in the sidebar:

```sh
GRIPI_RESOURCE_MONITORING=1
```

The indicator shows the cgroup total, the gateway’s memory, and the memory and number of Pi processes, including subagents. The parts may not add up to the total because shared memory is counted differently. 100% CPU means one full core. If cgroup data is not available, the indicator stays hidden.

## RPC diagnostics

To investigate a stuck Pi process, log its lifecycle:

```sh
GRIPI_RPC_DIAGNOSTICS=1
```

The log includes request and session paths, RPC command types and IDs, rejections, responses, timeouts, and process shutdowns. Prompts and conversation contents are never logged.

## Self-updates

On Linux and macOS, Gripi checks `origin/master` when the page loads and shows a sidebar control when an update is available. Anyone who can use the gateway can start an update.

The update waits until no Pi session is running. Gripi first builds the new version in a separate worktree and checks that it works with this machine’s Pi, so a failed update leaves the running gateway unchanged. If a later step fails, Gripi restores the previous version. Updating needs network access and can take a few minutes.

The checkout must:

- be on `master`
- have no changes, including untracked files
- have no local commits
- be able to fast-forward to `origin/master`

Gripi restarts itself only when it was started with `bin/start` or `mise run start`. Otherwise, it stops after updating, and you must start it again.

## Gateway state

Gripi stores its own data separately from Pi’s. Each location can be changed with the listed variable:

| Default location | Contents | Variable |
| --- | --- | --- |
| `~/.config/gripi/pinned-dirs` | Pinned session directories | `GRIPI_SESSION_CWDS_PATH` |
| `~/.pi/gripi/browser-access.json` | Approved browsers and access requests | `GRIPI_BROWSER_ACCESS_PATH` |
| `~/.pi/gripi/workspace-access.json` | Approved user tokens | `GRIPI_WORKSPACE_ACCESS_PATH` |
| `~/.pi/gripi/workspace-secret` | Key that links user tokens to users; deleting it disconnects every user from their sessions | `GRIPI_WORKSPACE_SECRET_PATH` |
| `~/.pi/gripi/session-owners.json` | Session owners in multi-user mode | `GRIPI_WORKSPACE_OWNERSHIP_PATH` |
| `~/.pi/gripi/read-state.json` | Read markers | `GRIPI_READ_STATE_PATH` |
| `~/.pi/gripi/pinned-sessions.json` | Pinned sessions | `GRIPI_PINNED_SESSIONS_PATH` |
| `~/.pi/gripi/session-tags.json` | Session tags | `GRIPI_SESSION_TAGS_PATH` |
| `~/.pi/gripi/environment.json` | Saved [environment variables](#environment-variables); contains secrets in plain text, so do not share it | `GRIPI_ENVIRONMENT_PATH` |
| `~/.pi/gripi/workers.json` | Workers added with `gripi worker` | `GRIPI_WORKERS_PATH` |
| `~/.pi/gripi/worker-placements.json` | Sessions moved to workers with `gripi worker move`, and what their returns kept aside | `GRIPI_WORKER_PLACEMENTS_PATH` |
| `~/.pi/gripi/attachments/` | Uploaded attachments | `GRIPI_ATTACHMENTS_ROOT` |
| `~/.pi/gripi/web-push-vapid.json` | Web Push keys | `GRIPI_WEB_PUSH_VAPID_PATH` |
| `~/.pi/gripi/push-subscriptions.json` | Web Push subscriptions | `GRIPI_PUSH_SUBSCRIPTIONS_PATH` |
| `~/.pi/gripi/restart-request` | Restart signal for `bin/start` (not read from the env file) | `GRIPI_RESTART_PATH` |
| `~/.pi/gripi/gripi.sock` | Socket for the [`gripi` command](../README.md#command-line), which must run with the same value (not read from the env file) | `GRIPI_SOCKET_PATH` |

Gripi’s state folder, the folder of `read-state.json`, also holds Gripi’s Pi extensions in `pi-extensions/` and, for [workers](#workers), SSH’s control sockets in `ssh/`, each worker’s `gripi` socket in `workers/`, main’s side of each session on a worker in `moves/`, and what returns kept aside in `returns/`.

If a file is malformed, Gripi leaves it untouched instead of replacing it. Requests that depend on it fail, and the gateway log names the file. To recover, stop the gateway, back up the file, then fix it or move it aside. Moving a file aside resets only its own data, such as approvals or read markers. Pi’s session files are not affected.

## Parallel development instances

A second gateway can read the same Pi sessions, but it must not change a session that another gateway or Pi process is using. Give it its own port and its own paths for every file in [gateway state](#gateway-state), and only change sessions dedicated to that instance.
